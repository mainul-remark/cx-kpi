1. System overview

CX Team KPI is an internal operations application for recording daily customer-experience work, attendance, leave, targets and KPI performance. It uses Laravel authentication, Jetstream teams, Sanctum sessions, an ACL package for route permissions, server-side DataTables, queued Excel/CSV exports, and activity logging.

Technology: Laravel 12, PHP 8.2/8.3, Blade, Livewire/Jetstream, Sanctum, MySQL-style migrations, Yajra DataTables, Laravel Excel, Spatie Activity Log, Uzzal ACL and Vite/Tailwind dependencies.

2. Roles, sectors and access control

Access is decided by two separate concepts. Sector controls data scope and business behavior; ACL role permissions control which routes/actions a user may open.

ActorData scope and behaviorTypical pages
Field sectorCan check in/out. Dashboard, attendance and KPI are forcibly scoped to the signed-in user. May submit reports and request leave. KPI targets are removed from responses.Dashboard, Day End, Report History, My Leaves, Attendance, KPI
Corporate sectorCan view team-wide reports/metrics, select users, see targets and live team status, edit another user's report, adjust attendance, and export KPI. Does not use the field check-in endpoints.Team Reports, Attendance management, KPI/export, targets, leave administration
ACL rolesRoles hold resource/action permissions generated from routes. Menu links appear only when the matching permission is granted. A sector alone does not grant a page.Roles, Users, permission list and any protected business route
Super adminAdditional hard-coded authority is required to delete users and roles. A super admin cannot delete their own user account from the admin Users page.User/role deletion

Most application routes use this middleware chain: authenticated Sanctum session → Jetstream session authentication → verified check → required-report check → ACL resource registration → ACL authorization. The header attendance endpoints deliberately omit ACL so any authenticated field user can use them.

3. Global rules and conditions

Authentication and session rules

  • / redirects authenticated visitors to /dashboard and guests to /login.
  • Login uses email, lowercases the username and is limited to five attempts per minute per email/IP. Two-factor challenges are also limited to five per minute.
  • Registration, password reset, profile update, password update and confirmed two-factor authentication are enabled by Fortify. Email-verification functionality is disabled in Fortify configuration, although protected routes include the standard verified middleware.
  • Jetstream team management, invitations and account deletion are enabled. API token UI and Jetstream profile photos are disabled in configuration.

Required prior report gate

Blocking condition: if a field user checked in on a previous day and has no report for their latest prior attendance date, every normal protected GET page redirects to the Day End form. AJAX/JSON requests and the report create/store/edit/update routes are exempt. The same debt also prevents a new check-in.
  • Only the latest prior attendance day is checked; older unreported days are not independently demanded.
  • The system—not the user—chooses a report date: owed previous attendance date, otherwise today.
  • Submitting that report clears the gate. If its old session was forgotten, the service fills 11:59 PM but keeps the session marked incomplete.

Calendar rules

  • Friday is the weekly off day. The working week begins Saturday.
  • Working-day range operations skip Fridays and all configured holidays.
  • Adding/updating a holiday deletes daily targets already set for that date.
  • A full approved leave day prevents a daily report. A half-day leave is still a worked/reportable day and halves applicable daily KPI targets.
  • A full-day leave cannot be created or approved where a report already exists; use half-day leave or delete the report first.

4. Main end-to-end workflows

Field employee day

Log in→Prior report check→Check in→Perform work→Check out→Submit Day End
  1. If a prior check-in lacks a report, the employee must submit that report before checking in or navigating the system.
  2. Check-in optionally records browser geolocation, accuracy, IP and user agent. Double clicks cannot create duplicate open sessions; an existing open session is returned.
  3. The header state shows check-in status, checkout reminder and any forgotten-session warning.
  4. Check-out closes the current session. If none is open, it returns a harmless “not checked in” response.
  5. Day End saves one report per user/date. Existing data for that date is updated. Active project/platform fields depend on their activity switches.

Management cycle

Configure projects/platforms→Maintain holidays→Set targets→Review reports/attendance→Review/export KPI

Managers first define active work channels and which activity fields each channel supports. They maintain the work calendar, set daily or monthly targets, decide employee leave requests, correct attendance when necessary, and then monitor dashboards/KPI. Closed-month KPI is frozen on the first day of the following month.

Leave request workflow

Field user requests→Pending→Manager approves or rejects→Approved leave affects attendance/KPI

A user-created request is pending and does not affect calculations until approved. An admin-created leave is approved immediately. Pending requests can be withdrawn by their owner; decided requests cannot. Approval rechecks report conflicts because a report may have been submitted after the request.

5. Page-by-page guide

5.1 Dashboard — /dashboard

Field: own dataCorporate: team/user filteradmin.dashboard

The shell loads first; Overview, People, Attendance and Live sections are fetched independently by AJAX so a slow section does not block the others.

SectionExplanation and logic

5.2 Attendance — /attendance and header check-in

Field: own attendanceCorporate: all usersattendance.index

Attendance sheet

Shows one mark per user/day: P present (report exists), A absent, L approved full leave, O Friday off, H holiday, F future, and N before the user was created. The page supports the common presets/custom range, user filter for corporate viewers, server paging (5–100 rows) and full CSV-style JSON export.

Check-in log

Groups multiple sessions into one user/day row: first check-in, final checkout, sum of completed-session minutes, session count, status and last adjustment note. Status priority is open → incomplete → adjusted → completed. Managers additionally receive coordinates and editable timestamps; field users do not receive locations.

Check-in/check-out conditions

  • Only field users; calls are throttled to 10 per minute.
  • Location is optional. Latitude must be −90..90, longitude −180..180 and accuracy non-negative. A partial coordinate pair is discarded.
  • Only one open session per user is allowed. Stale prior-day sessions auto-close without a known checkout time.
  • At 7:00 PM attendance timezone, open users receive a database notification. Checkout or acknowledgement marks it read.
  • A corporate manager may adjust the session ending the day. Checkout is required, cannot precede check-in or be future; optional check-in must remain on the original work date. A reason is required and the change is activity-logged.

5.3 Daily reports

Day End — /daily-reports/create

Primary field workflowdaily-reports.create/store

The report date is read-only and selected by the attendance service. If a report already exists for that user/date, the form is prefilled and saving updates it instead of creating a duplicate.

Input groupRules

Team Reports — /daily-reports/team

Same listing, with a field-user selector. ACL access to this route is what exposes the team menu item; it should be assigned only to appropriate roles.

5.4 Daily and monthly targets

Daily Targets — /daily-targets

Managementdaily-targets.*

  • List one target per field user/day, filter by user and date, and view platform/project breakdowns and setter.
  • Create/edit applies one definition to one or more field users across working days. Fridays and holidays are skipped; an empty working-day range is rejected.
  • Outbound target is required and ≥1. Other main/entity targets are optional non-negative integers. Only active project/platform IDs are accepted.
  • Existing target for user/date is replaced as a whole, including its child activity rows. Empty optional activities become “no target.”
  • CSV export uses the visible filters. It queues a job, returns a user-owned token, supports status polling, then serves the completed file once and deletes it.

Monthly Targets — /period-targets

One monthly target per field user/activity, used only when KPI_TARGET_MODE=period. Select month and users, enter required outbound target and optional activity targets. Saving replaces each selected user's entire month. Blank/zero activities are omitted. Deleting removes all of one user's targets for that month.

Mode choice: daily compares each day's report to that day's target. period prorates a monthly target by eligible working days in the requested range, excluding pre-join days and approved leave; the UI still contains both target-management pages, but KPI reads the configured mode.

5.5 KPI — /kpi

Own score, targets hiddenTeam scores and exportkpi.*

  • Uses the same presets/custom range and 366-day limit. Corporate users can filter a field user; field users are forced to themselves.
  • Daily detail labels each working day as worked/absent/leave/off/not joined. Attendance check-in figures are informational and do not change score.
  • Report outbound calls and order processing are added together and compared with the outbound target.
  • Every activity with a positive target gets a score share. Outbound receives the configured 70% when other target activities exist, otherwise 100%. Other target activities split the remainder equally. If outbound has no target, other activities split 100%.
  • Each activity achievement is capped at 100%; total score is capped at 100. The default totals weight only outbound at 1 and give other metrics weight 0, although those activities can still have their own score lines.
  • Half-day approved leave halves a daily goal using ceiling rounding. Full leave is excluded. A missing report on a working day is absent.
  • Corporate Excel export is queued, token-owned, single-download and automatically purged if abandoned. It contains one sheet per user.
  • /kpi/monthly returns frozen snapshots. Default is the prior month; corporate sees all, field sees self. Snapshots prevent later edits from rewriting historical closed-month scores.

5.6 Leave pages

My Leaves — /my-leaves

Lists the signed-in user's daily leave rows, newest first, including decision status and approver. Only field-sector users can apply. Valid types are Casual, Sick, Annual and Other; duration is Full Day or Half Day.

  • Range must contain at least one working day and may span at most 31 days.
  • Existing approved leave cannot be overwritten by another request.
  • Full-day request conflicts with an existing report; half day does not.
  • Each working day becomes a pending row. Only pending rows can be withdrawn, and only by their owner.

Leave Administration — /leaves

Lists all field-user leave rows with user/date/status filters. Admin-created leave is approved immediately and may be bulk-applied over users/working days (up to 366-day span). Existing user/date leave is replaced. Editing remains a single day and cannot move onto Friday/holiday or duplicate another leave.

Approving a pending full day rechecks report conflicts. Approve/reject records the deciding user. Editing an already approved leave updates its approver to the current administrator; pending/rejected decisions remain unchanged. Deletion removes the record; daily targets are deliberately retained so they count again if leave is removed.

5.7 Master-data pages

Projects — /projects and Social Platforms — /social-platforms

Both pages are AJAX CRUD lists with the same behavior: unique name (max 255), optional notes (max 5,000), active flag, and switches for outbound calls, comments and message replies. Unchecked switches normalize to false. Slugs regenerate from changed names and receive numeric suffixes if needed.

An entity referenced by report or target data cannot be deleted (HTTP 409); deactivate it instead. Active entities appear on new reports/targets. An inactive entity remains accepted on a report that already contains it so historical data can be edited.

Holidays — /holidays

AJAX list/create/edit/delete. Date must be unique; title is required, max 255. Import accepts XLSX/XLS/CSV up to 5 MB, expects Date and Title headings, reports row failures, and updates/creates valid holidays. Sample XLSX or CSV is downloadable. Saving a holiday removes daily targets on that date.

5.8 Administration pages

Users — /admin/users

Lists users and roles, with role filtering. Create/edit requires name, unique email, employee ID, at least one role, sector (field/corporate), active boolean and optional image under roughly 1 MB. New password requires 8+ characters with uppercase, lowercase, digit and one of @ # $; edit password is optional with the same complexity.

Import accepts XLSX/XLS/CSV up to 5 MB with User Name, Email, Employee ID, Usages Sector and Role. Email/employee ID must be unique both in the database and file; role must exist. Valid rows get default password remarkhb and one role. Any row failures produce a failure response while valid rows may already have been imported; the operation is audit-logged.

Only a hard-coded super-admin role can delete a user, and self-deletion is blocked. The profile image file is removed before the user record. The is_active field is stored/displayed, but this codebase does not add it as a Fortify login condition.

Roles — /admin/roles

Create/edit a slugged unique role name (max 30) with at least one ACL resource. Resources for Role/Resource controllers are excluded. Updating replaces permissions. Only super admin may delete; role ID 1 is excluded from normal lists/forms.

Permission Labels — /view-permissions

Lists generated ACL resources grouped/sorted by controller and allows their human-readable labels to be updated. The update endpoint does not declare field validation in the controller.

Activity Log — /admin/activity-log

Paginated 15 rows with total/today/auth/data/workflow summaries. Filters: free text, event, log name, subject type, causer and date range. Search scans description, event, log name, subject/causer type and JSON properties.

Site and Theme Settings — /site-settings

Stores one effective site-settings record: title/meta text, custom header/footer code, contact details, site information, favicon/logos/banner and layout theme. Images are validated by type/size and old files are deleted on replacement. Phone accepts Bangladeshi mobile formats. Theme values are restricted to defined styles and RGB triplets. The menu link is currently commented out, so access is normally by route/permission or theme switcher.

9. Implementation notes and operational cautions

These are documented behaviors observed in the current source, useful for administrators and future developers.

  • Public registration vs employee data: registration is enabled but does not set employee ID, sector or ACL roles. Such a user may authenticate but will not automatically fit normal field/corporate authorization workflows.
  • Active user status: is_active is managed in the Users page, but the Fortify provider shown in this project does not reject inactive users during authentication.
  • Email verification: the protected group uses verified, while the User model does not implement MustVerifyEmail and Fortify email verification is disabled. This effectively relies on Laravel's behavior for non-verifying users.
  • Password-expiry middleware: a 30-day password middleware exists but is not attached in the reviewed route group, and it references a named reset route not declared in project routes. Treat it as dormant unless enabled elsewhere.
  • Import atomicity: user import validates rows and imports valid rows in a transaction, but returns an overall 422 when any row failed. Administrators should check imported_count before re-uploading to avoid confusion.
  • Public utility route: /optimize-clear has no authentication middleware in routes/web.php. Restrict it at deployment or move it behind authorization if it should not be public.
  • Menu vs route: site settings, permissions and activity log may not all appear in the sidebar. ACL-authorized routes still exist and can be opened directly.
  • Labels in legacy schema: child column inbound_calls is displayed as outbound calls in project/platform forms due to a historical schema rename. Documentation follows the UI/business wording where relevant.
Source of truth: this document describes the repository as reviewed on the date above. Environment values such as KPI_TARGET_MODE, queue driver, application timezone, mail and filesystem configuration can change runtime behavior.
